# WO Tracker

Personal work order tracker for electrical distribution work (SEC work orders 401–805):
Windows desktop app plus Android app, fully offline, synced through Supabase, with daily reports.

Design: see the "Work Order Tracker — System Design" doc and the "Work Order Tracker Screens" design canvas.

## What is in this repository

## Safety rules built into the database

- Nothing can be permanently deleted, not even by the database administrator. "Delete" sets `deleted_at`, and the row can be restored.
- Every insert, change, delete and restore is written to `activity_log`, which cannot be edited.
- Row-Level Security: each account sees and changes only its own rows; signed-out visitors see nothing.
- Validation in the database itself: 9-digit extension numbers, no duplicate work order or tasreeh numbers, no dates in the future, tasreeh end after start, segment widths 40 or 80, and more.

## Running the tests

```bash
# Rules engine (needs Node.js 20+)
cd tools/rules-check && node --test

# Database tests and backup rehearsal (needs PostgreSQL 16+ installed)
supabase/tests/run.sh
supabase/tests/backup_restore.sh

# Attachment backup rehearsal: the folder layout, the tar archive, the "every restored row
# has its file" check and the encrypt/decrypt round trip (needs bash; gpg tested if present)
supabase/tests/attachment_backup.sh

# Dart engine against the same scenarios (needs Flutter)
cd app && flutter test
```

## First-time setup on the PC

Each step takes about 5 minutes. Claude walks through them one at a time.

1. **GitHub:** create a private repository named `wo-tracker`, then push this code to it.
2. **Supabase:** create a free project (region closest to Riyadh), open the SQL editor and run the files in `supabase/migrations/`, in name order. The second creates the `powersync` publication PowerSync needs; the third adds the database-size check used by Data health and the nightly backup; the fourth adds reminders (the app works without it, but reminders only stay on the device until it is run and the sync rules below are redeployed). The fifth creates the private `attachments` storage bucket (25 MB per file, free plan 1 GB) so attached photos and files are backed up and appear on every device; without it they stay on the device that added them.
3. **PowerSync:** create a free account, connect it to the Supabase project, and paste `powersync/sync-rules.yaml`. Free PowerSync projects are switched off after a week without use; if you are away longer, switch it back on in the PowerSync dashboard (no data is lost, the devices catch up).
4. **Flutter app:** install Flutter (stable) and Visual Studio 2022 Build Tools with "Desktop development with C++" (both free). Then in PowerShell, from this folder:
   `powershell -ExecutionPolicy Bypass -File scripts\setup-app.ps1 -Android -Installer`
   This adds the Windows and Android folders (without touching our code), checks the code, runs every test, and builds the Windows app, the Android APK and the Windows installer (`build\WO-Tracker-Setup-<version>.exe`, needs the free Inno Setup 6). Leave out `-Android` or `-Installer` to skip those.
   First start: the app opens with no data and works offline straight away. Settings → Sync → enter the Supabase URL, anon key and PowerSync URL, then sign in. The first time, use "Create account"; Supabase sends a confirmation email. Click its link (the page it opens may not load; the account is confirmed anyway), then sign in. Or switch off "Confirm email" under Supabase → Authentication → Sign In / Providers → Email before creating the account. Settings → Demo mode shows sample orders without touching real data.
   To update later: build again and run the new installer over the old one. The data is kept in the Windows app-data folder, which install, update and uninstall never touch.
5. **Backups:** add the secrets listed at the top of `.github/workflows/nightly-backup.yml`, then run the "Nightly backup" workflow once by hand to check it. When making the rclone config for Google Drive, leave "client_id" empty (rclone's own Google client). A Google Cloud app of your own left in testing mode would stop working after 7 days.

   Two things are easy to get wrong and both are guarded now:

   - **The attachment files are stored in the Supabase Storage bucket, not in the database,** so a database dump alone cannot bring your photos and PDFs back. `SUPABASE_SERVICE_KEY` lets the nightly job copy them into `wo-<date>.storage.tar.gz.gpg` next to the dump. Without that secret the job still saves the rows but prints a loud warning and writes `wo-<date>.storage-SKIPPED.txt`, and the weekly restore test warns too. Restoring such a backup gives you every order and step, with attachments pointing at files that do not exist.
   - **`BACKUP_PASSPHRASE_ESCROW` must hold a copy of `BACKUP_PASSPHRASE`.** The nightly run fails if it is missing or does not match. This is deliberate: if the only copy of the passphrase is the GitHub secret and that secret is lost, every backup becomes permanently unreadable, and you would only find out when you needed one. Keep the real copy outside GitHub, in a password manager.

6. **Backup on this computer (no account, no internet).** Two ways, both keep everything — orders, photos and settings:

   - **In the app:** Settings → **Backup on this computer** → **Back up now** writes one `.zip` wherever you choose. **Restore from a backup** reads it back and replaces everything; a copy of the current data is first kept beside the data folder as `wo_tracker_data_before-restore_<time>`, so a wrong file can be undone. The database is closed while its files are replaced, then reopened.
   - **On a schedule:** `scripts/local-backup.ps1` writes the same `.zip` to `Documents\WO-Tracker-Backups` (newest 30 kept) without opening the app. Register it in **Task Scheduler → Create Basic Task** (Daily, Weekly or Monthly) with *Start a program*:
     `powershell.exe -ExecutionPolicy Bypass -WindowStyle Hidden -File "<repo>\scripts\local-backup.ps1"`

     It reads the database with shared access, so it also works while the app is open. A backup made this way is accepted by **Restore from a backup** in the app (the same file format is used).

   The backup is a `.zip` of the device folder: `wo_tracker.db` (+ the `-wal` file when it has unmerged writes), `shared_preferences.json` and the `photos/` folder, plus a `backup.json` that names the app and format so a wrong file is refused rather than half-restored.

## Rules for the app's data layer

The database and sync were reviewed for two devices editing while offline. The Flutter data layer must follow these rules:

1. **Step rows have the same id on every device:** `stepRowId(work order, step, segment, meter)` in `tools/rules-check/ids.mjs` (a version 5 UUID; in Dart, `StepIds.stepRowId` in `app/lib/data/ids.dart`, plain Dart with no package, checked against `app/test/fixtures/ids.json`). Steps are uploaded with insert-or-update, and clearing a step updates the same row (`done_date` and `not_applicable` cleared, the note kept). Two devices marking the same step then end up with one row instead of a refused upload that blocks the sync queue.
2. **The device never sends `owner_id`, `created_at` or `updated_at`;** the server sets them. That keeps ownership safe and the weekly restore check exact.
3. **Nothing is ever deleted;** "delete" sets `deleted_at` (the database refuses real deletes).
4. **Every order of a meter type has at least one meter row from the start** (its number can come later), and segment and meter ids never change when an order is edited. Step records are tied to those ids.
5. **An upload the server refuses** (for example the same work order number typed on two devices while offline) goes to a "Needs your decision" list in the app instead of retrying forever. `classifyUploadError` (`tools/rules-check/upload-errors.mjs`, Dart: `UploadErrors.classify` in `app/lib/data/upload_errors.dart`) decides: retry later (offline, server busy or waking up, order not uploaded yet), sign in again, or needs your decision. The refused change stays on the device until it is edited and saved again or undone.
6. **Data health shows the database size** against the free plan's 500 MB, with a warning at 80% (`select public.data_health()`). The nightly backup runs the same check (`scripts/check-db-size.sh`) and fails, so GitHub emails you, once it passes 80%. Measured growth is about 60 MB a year at 14 orders a day.

## If you ever need to restore a backup

1. Download the newest `wo-YYYY-MM-DD.dump.gpg` from Google Drive (`WO Tracker/Backups/database/`), and its `wo-YYYY-MM-DD.storage.tar.gz.gpg` if there is one.
2. Decrypt it: `gpg --decrypt wo-YYYY-MM-DD.dump.gpg > restore.dump` (asks for the backup passphrase).
3. Restore it into the Supabase project with `pg_restore --no-owner --no-acl`.
4. Run `supabase/recovery/reapply_grants.sql` and `supabase/migrations/20261011000002_powersync_publication.sql` in the Supabase SQL editor.
5. **Attachments:** decrypt `wo-YYYY-MM-DD.storage.tar.gz.gpg` into `attachments/`, then upload every file back into the private `attachments` bucket at the same path. Each file's path is the row's `storage_path` (`<user id>/<attachment id>.<ext>`), so:
   `select storage_path from public.attachments where storage_path is not null;`
   Until the files are back, the orders look complete but photos and PDFs will not open.
6. **Only if this is a new Supabase project:** open the app and sign in once, then run `supabase/recovery/reassign_owner.sql` with your new user id pasted in (the file explains where to find it). Without this step the app shows nothing, because every row still belongs to the old account's id. Attachment files uploaded in step 5 use the **old** user id in their folder, so after the move also copy them (or re-upload) into the new user's folder, or the app cannot read them.

Keep the backup passphrase somewhere safe outside the app (for example a password manager), and put a second copy in the `BACKUP_PASSPHRASE_ESCROW` secret. Without the passphrase the backups cannot be opened, and the nightly job now refuses to run if that second copy is missing.
